## 🏢 Business Processes Impacting Security
Change management isn't just about technical updates; it’s a formal business process designed to prevent "self-inflicted wounds" to an organization's security posture.

### 1. The Approval Framework
* **Approval Process:** Every non-emergency change must be reviewed and authorized. This is often handled by the **Change Advisory Board (CAB)**.
* **Ownership:** The person or department responsible for the system or data being changed. They are the primary decision-makers for that asset.
* **Stakeholders:** Anyone impacted by the change (e.g., end-users, management, other IT teams).

### 2. Risk Mitigation & Planning
* **Impact Analysis:** Evaluating the potential "blast radius" of a change. (e.g., "If we update this database, will the website go down?").
* **Test Results:** Proof that the change was performed successfully in a **Sandbox** or **Lab** environment before hitting production.
* **Backout Plan:** A documented "Undo" button. If the change fails, how do we return to the last known-good state?
* **Maintenance Window:** A pre-approved time slot (typically low-traffic hours) for implementing changes to minimize business impact.
* **Standard Operating Procedure (SOP):** The step-by-step manual that ensures the change is implemented identically every time.

## ⚙️ Technical Implications
Changes often have technical side effects that can create security holes if not managed carefully.



| Technical Factor | Description | Security Impact |
| :--- | :--- | :--- |
| **Allow lists/Deny lists** | Updating firewall or application rules. | An incorrect rule could block legitimate traffic or let attackers in. |
| **Restricted Activities** | Disabling certain user actions during a transition. | Prevents data corruption while a system is being updated. |
| **Downtime** | The period when a service is unavailable. | Can be mistaken for a DoS attack if not communicated. |
| **Service/App Restart** | Many patches require a reboot to take effect. | If the service fails to restart, Availability is compromised. |
| **Legacy Applications** | Older software that may not support new security patches. | These are major vulnerabilities; changes often require "Compensating Controls." |
| **Dependencies** | When System A relies on System B to function. | Changing System B can break System A if dependencies aren't mapped. |

## 📂 Documentation & Version Control
Documentation is what separates a "professional environment" from a "chaotic one."

### Updating Documentation
* **Diagrams:** Physical and logical network maps must be updated to reflect new hardware or IP addresses.
* **Policies/Procedures:** If a change modifies how users access a system, the AUP or Security Policy must be updated.

### Version Control
This is the practice of tracking and managing changes to software code, configuration files, or documentation.
* **Rollback:** The ability to quickly revert to a previous version if the current one is unstable.
* **Audit Trail:** Knowing exactly **who** changed **what** and **when**.

| :--- | :--- | :--- |

| **RFC** | Request for Change | The formal document used to propose a change. |
| **UAT** | User Acceptance Testing | Ensuring the change meets the needs of the end-user before full rollout. |

## 💡 Exam Tip
> [!IMPORTANT]
> **Scenario:** A technician installs a critical security patch on a Friday night without telling anyone. On Saturday, the system crashes, and no one knows why. 
> **Question:** What was the primary failure?
> **Answer:** Lack of **Change Management** (specifically lack of Communication and Stakeholder involvement).

## 🏁 Quick Knowledge Check
1. **What is a "Backout Plan"?** A strategy to revert a system to its previous state if a change fails.
2. **Who approves major changes?** The Change Advisory Board (CAB).
3. **True or False:** Testing should be done in the live production environment. (False - always use a lab/sandbox).
